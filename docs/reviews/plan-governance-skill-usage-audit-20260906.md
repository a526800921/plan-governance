## 用户已确认的使用场景

- 实际项目样例是 Docker 中的 NAS Git 服务和 TunnelPad。通常先提出想做的功能，再通过 grilling 确认实现方式，随后连续实施。
- AI 先进行功能测试与运行验证；用户再通过查看、操作等方式验收，确认符合预期，并观察 CPU、内存、磁盘读写是否异常。
- 对采用这一工作方式的功能计划，用户验收通过后才关闭。新的点子或较大改动另开计划。
- 自测或独立复核发现普通问题时，在已授权范围内自行修复、重新验证和送审。用户确认“小问题不要升级给我”；新的取舍、授权变化或无法自行解决的阻塞仍需用户参与。
- 用户已确认优化方向：保留 grilling、证据、必要独立复核与事实源分工，完善连续推进、技术验收、用户验收和修复流程。
- 用户进一步反馈目前复核时间占用较多，并明确要求将下述三项反馈闭环改进及复核减负建议纳入本交接报告。此确认授权更新报告，具体规则仍待承接设计和验证。

本轮确认的是工作方式和优化方向，当前动作是文档准备；没有因此获得修改已安装 skill、代码、测试、分发清单、发布或外部项目的实施授权。

## 补充交接：反馈闭环的三项改进

用户要求纳入以下方向。优先复用已有需求探索、用户可观察验收及验证记录，不新增固定文档组合，也不把每个小动作变成用户确认点。

| 改进 | 拟议行为 | 适用边界 |
|---|---|---|
| F01 提前明确可观察验收 | grilling 收敛时留下少量具体场景：前置/输入、操作、可观察结果；功能涉及资源开销时，同时确定相关性能指标和比较基线 | 复用已确认场景，避免追问实现细枝末节；性能阈值由项目需求和实测基线确定，未确定的标准明确保留为待确认项 |
| F02 提前体验不确定功能 | 对交互、操作流程或方案存在明显不确定性的功能，先完成关键流程或最小可运行结果，让用户尽早体验并校准方向，再完成其余部分 | 明确的小改直接推进；体验不等于最终验收，不强制每阶段签收。可以继续不依赖反馈的工作，涉及尚未确认的关键取舍时等待回答，不能把未回复当作接受 |
| F03 保留可复验的技术结果和最终用户验收 | AI 先完成适用的功能、实际运行及相关性能验证，留下命令/步骤、条件和实际结果；原范围小缺陷自行修复、复验，触发复核时重新送审；交付试用入口和场景，用户接受后才关闭功能计划 | 技术验证通过与用户接受分别记录；不能保证不存在任何缺陷，不能以状态或测试通过代替实际体验，也不以“小问题”名义扩展授权和架构 |

性能观察按功能影响选择空闲、典型负载或持续运行场景，在可比环境、负载和观察窗口下比较修改前后。用户的观察可以发现异常，AI 负责补充可复验依据；纯文档修改不要求 CPU、内存、磁盘读写采样。

### 待承接的四项减负设计

| 改进 | 拟议行为 | 保留的约束 |
|---|---|---|
| R01 按风险设置独立复核时点 | 对范围明确、可逆的普通修改，评估以完成时一次独立复核覆盖需求和实现；高影响方案保留实施前审查，避免仅因拆成多个内部步骤就重复设门 | 风险按契约、数据、权限、迁移、发布和可逆性判断，不能只看代码行数。现行逐阶段准入要求不会因本报告取消；适用分类和兼容规则需先在正式规范中确定 |
| R02 缺陷重审聚焦变化范围 | 重审检查原阻塞是否解除、修复差异及受影响回归；未变化且证据有效的部分引用原记录 | 仍由独立复核者作出新结论并保留失败历史；发现新行为变化、共享依赖影响或证据失效时扩大检查，不能用自测清除复核阻塞 |
| R03 复用可信完整验证证据 | 对同一受审工作树及相同验证条件，复核者核对实际命令、结果和覆盖范围，并亲自复验关键风险点；无新的失效原因时可复用完整测试证据 | 不能只比较版本号或 HEAD；需核对相关源码/测试、未提交差异、依赖、配置、环境及验证契约。仅有实施者“通过”声明不够；证据缺失、冲突或相关变化时补做相应验证。既有 CI/发布强制检查仍执行 |
| R04 合并行为后测与完成复核 | 适用时由同一独立复核任务完成 skill 行为样本和完成条件核对，共享必要上下文与证据，减少重复派发和报告 | 复核者不得参与受审实施或测试编写；行为测评仍先依据受审 skill、模板和原始请求作答，再对照预期，防止答案泄漏；行为结果与机械验证结果分别记录 |

复核输出聚焦正确性、已确认需求和实际风险；可选风格或优化建议不自动变成阻塞。相同检查无新证据时停止无效重复，保留问题并调整排查方法；确实无法自行解决时报告。后续效果评估优先复用已有派发和执行记录，区分复核耗时、实际阻塞等待及有效缺陷发现，不新增每个小任务必须填报的计时表。

## 历史协调建议

以下保留最初“合并到现有计划”的讨论，已被用户选择独立后续计划的决定取代。当前安排见本文开头和新计划，本节不作为继续合并或实施的指令。

初次审计及本轮补充时，任务“优化项目治理规范”正在同一工作区处理阶段 3。为保持单一写入，本任务只维护用户点名的本报告，没有并发修改专项计划、地图、阶段样本或规则源。

建议由承接任务的写入负责人统一吸收本轮确认，先核对届时最新阶段和已批准范围。能在现有计划承接的内容不新建重叠计划；超出当前阶段的复核策略和证据复用变更，须先确定后续承接位置，不能静默混入已经通过的范围。以下两处仍需协调：

1. 当前契约称“场景不是逐次用户签收的新门禁”。应保留每个小动作和内部阶段无需用户签收的边界，同时补充本轮已确认的功能计划最终用户验收。二者的作用范围不同，不能把内部阶段完成自动等同于用户接受整个功能。
2. 当前契约称“分流不覆盖独立复核失败的停止规则”。应继续阻断未通过的阶段放行，同时明确已授权范围内的补证据、修复和重新送审路径。失败历史不得改写，通过必须来自新的独立复核；入口不可用、证据冲突或问题无法收敛时，保留阻塞并报告。规则变更须与 [phase-local-review-dispatch](../plans/phase-local-review-dispatch.md#公共契约变化) 协调，不能由本报告单独生效。

F01—F03 优先复用用户可观察验收和反馈记录；R01—R04 涉及独立准入、复核调度及验证证据的现有契约，应与相关计划和检查器兼容边界统一设计。初次审计发现、三项闭环改进、四项减负设计分别确认承接位置；本报告不重开历史阶段，也不把旧准入或完成结论扩展到新增范围。

兼容方向建议：先复用现有阶段记录和生命周期枚举，记录 AI 技术结果、用户反馈及接受结论；不增加一个“待用户验收”枚举，不追溯重开已完成的历史计划，不把等待用户最终验收变成每个阶段都要确认。具体字段及旧文档兼容仍由阶段设计和独立准入确定。
