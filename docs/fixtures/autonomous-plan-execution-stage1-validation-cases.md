# 自主计划执行阶段 1 校验设计案例

本文件只属于 `autonomous-plan-execution` 计划，用于阶段 1 的 Step 0 和后续步骤表解析/校验实现。它不是事实源；字段、状态和分支语义以专项计划为准。

## 案例 V1：合法串行步骤表

### 输入

计划声明 `execution_mode: autonomous-continuous`、`execution_policy: serial`，并包含 `S1 -> S2 -> S3` 的七列表。

### 预期

- 校验结果为 `valid`。
- 步骤 ID 唯一，前置步骤均引用同一阶段已存在的 ID。
- `未开始 -> 执行中 -> 已完成` 等允许转换可被识别；不计算下一步骤，不执行动作。

### 失败判定

把自然语言“实施步骤”当作步骤状态事实；或校验过程中执行动作、写回计划。

## 案例 V2：合法并行声明

### 输入

计划声明 `execution_policy: parallel`，`S2` 和 `S3` 只共享写入提示，没有业务前置关系。

### 预期

- 校验结果为 `valid`。
- 保留 `shared_write_risk` 约束作为提示，不把它改写成前置步骤或自动降级为串行。
- 阶段 1 只校验表达合法；ready steps 集合和写入顺序由阶段 2 的 `next` 入口处理。

### 失败判定

因为存在共享写入提示就拒绝合法步骤表，或阶段 1 提前输出下一步骤集合。

## 案例 V3：旧计划和未启用模式

### 输入

- 旧计划没有 `execution_mode` 和执行清单。
- 计划有普通自然语言实施步骤，但没有结构化七列表。

### 预期

- 校验结果为 `not_enabled`。
- 既有基础/严格治理结果不变，不要求历史计划迁移。

### 失败判定

把未启用计划标为 `invalid` 并阻断已有治理检查，或从自然语言生成步骤 ID。

## 案例 V4：结构错误和严格模式

### 输入

分别构造：重复 ID、未知前置 ID、前置环、缺失动作/证据/完成条件、非法状态 `取消` 和缺少不适用分支证据；历史状态转换不在阶段 1 的单快照输入范围内。

### 预期

- 默认校验返回明确 WARNING 和 `invalid`，不得提供后续 `next` 可执行依据。
- `--strict-readiness` 或步骤严格模式把同一结构问题提升为 ERROR。
- 错误包含计划、阶段、步骤 ID 和字段定位，不修改原文。

### 失败判定

接受错误结构、静默删除错误行、把失败步骤标为完成，或在错误存在时继续交给执行者推进。

## 案例 V5：分支、证据和无写入

### 输入

- `S2` 进入 `不适用`，但只有在计划声明的条件、理由和替代证据齐全时才允许。
- 合法/非法 fixture 各运行一次校验，并记录文件 hash。

### 预期

- 合法分支通过；缺少触发条件、理由或替代证据时失败。
- 校验只读，不更新步骤状态、计划地图、Git 索引或外部系统。

### 失败判定

校验工具自动补证据、自动推进状态，或由于检查而改变文件内容。
