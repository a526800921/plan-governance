# plan-governance 防计划漂移优化分析

## 概述

本文档分析 `plan-governance` 在"防止计划跑偏"方向上的优化空间。所有建议均在当前轻量定位框架内，不引入重型流程。

---

## 一、检查脚本盲区

### 1. 证据"存在性检查"强，但"有效性检查"弱

**现状**：`has_completion_evidence()` 只检查 `Step 0 证据`/`验证方式` 章节标题是否存在，不验证内容。对比 `has_coverage_evidence()` 已实现内容级校验（匹配百分比、`pytest`、`coverage` 等关键词）。

**风险**：计划文档只写了标题、内容为空或纯占位符，检查脚本也会通过。

**建议**：对 Step 0 证据章节做内容级验证，要求至少包含以下任一可识别模式：

- 可执行命令（如 `python3 -m pytest`、`bash ...` 等代码块）
- 文件路径引用（如 `tests/`、`fixtures/`、`samples/` 等）
- 版本号或基线标识（如 `v1.2.3`、`commit abc123`）
- 明确的复现步骤描述（不少于 N 字符）

```python
# 示意：has_completion_evidence() 增强
def has_completion_evidence(plan_text):
    # 1. 章节标题存在
    # 2. 章节内容非空
    # 3. 包含可执行命令、文件路径、版本号或复现步骤
    ...
```

### 2. 没有"计划停滞"检测

**现状**：一个计划停留在"实施中" 6 个月没有任何告警。系统对时间完全不敏感。

**风险**："实施中"变成僵尸状态，实际已经放弃但无人标记，后续计划可能基于错误的状态信息做决策。

**建议**：

- `PLAN_MAP.md` 的计划索引增加 `最后更新` 列
- 检查脚本新增 `--stale-days N` 参数，默认对超过 90 天未更新的"实施中"或"待实施"计划发出警告
- 不强制阻断，仅作为提醒

```markdown
| 计划 | 状态 | 当前阶段 | 最后更新 | 依赖 | 证据 |
|---|---|---|---|---|---|
| example-plan | 实施中 | 阶段 1 | 2026-01-15 | - | [验证] |
```

### 3. 没有"已完成计划被修改"检测

**现状**：如果有人修改了一个已标记"已完成"的计划文档（改了完成条件、字段方案等），系统完全无知。

**风险**：已完成计划是一份"冻结"的契约记录，修改它意味着历史契约被悄悄改写。后续审计和回溯失去可信度。

**建议**：

- 计划完成时在文档中记录完成证据摘要（当前已有）
- 检查脚本对已完成计划计算当前内容与完成时证据摘要的差异
- 简单方案：记录完成时的文件 hash，后续检查时比对；hash 变化时警告
- 更轻量方案：在 `PLAN_MAP.md` 完成证据列旁增加 `证据摘要` 字段，记录完成时的关键指标（测试数、覆盖率数值、验证命令输出摘要），检查时交叉比对

## 二、多计划之间的语义冲突

### 4. 同模块多计划无冲突检测

**现状**：只检查依赖环和"实施中计划是否依赖了已废弃计划"。如果计划 A 和计划 B 都要修改同一个模块，且方案互相矛盾，当前系统不会发现。

**风险**：两个活跃计划同时修改同一文件/模块，后合并的那个可能静默覆盖前者的工作。

**建议**：

- 计划文档模板已有"影响模块或文件"章节
- 检查脚本新增交叉比对：扫描所有活跃计划（候选、设计中、待实施、实施中）声明的"影响模块或文件"
- 发现重叠时标记为 `WARNING`，提示需人工确认是否存在冲突

```python
# 示意：交叉比对影响文件
def detect_overlapping_targets(active_plans):
    file_to_plans = {}
    for plan_name, affected_files in active_plans.items():
        for f in affected_files:
            file_to_plans.setdefault(f, []).append(plan_name)
    return {f: plans for f, plans in file_to_plans.items() if len(plans) > 1}
```

### 5. 依赖声明与实际内容无交叉验证

**现状**：`PLAN_MAP.md` 的依赖表完全手写，计划文档正文中的交叉引用也靠手写，两者之间没有一致性检查。

**风险**：

- 计划文档正文引用了另一个计划（如 `[[multi-doc-sync-rules]]`），但 `PLAN_MAP.md` 依赖表没写 → 依赖关系丢失
- `PLAN_MAP.md` 声称计划 B 依赖计划 A，但计划 B 正文从未引用 → 依赖可能是过时的或臆造的

**建议**：

- 检查脚本扫描每个计划文档正文中的 `[[wiki-link]]` 或 `docs/plans/` 引用
- 与 `PLAN_MAP.md` 依赖表做交叉比对
- 报告两类不一致：
  1. "正文引用但依赖表缺失"
  2. "依赖表声明的依赖在另一计划正文中无引用"

```python
# 示意：交叉比对
def cross_validate_dependencies(plan_text, declared_deps):
    referenced = extract_plan_references(plan_text)  # 从 [[...]] 和 docs/plans/ 链接提取
    missing_in_map = referenced - declared_deps
    unreferenced = declared_deps - referenced
    return missing_in_map, unreferenced
```

## 三、漂移检查的自动化

### 6. 设计文档中的"漂移检查清单"仍为纯手动

**现状**：`plan-governance-design.md` 第 11 节列了 6 个漂移检查问题，全部依赖人工判断，实际执行率不可控。

**可半自动化项**：

| 检查问题 | 自动化可行性 | 方案 |
|---|---|---|
| 新信息是否违背既有 ADR？ | 低 | 保持人工 |
| 是否改变其他计划的前置条件/顺序？ | 中 | 比对计划依赖链是否因新计划插入而断裂 |
| 是否改变公共接口/Schema/兼容承诺？ | 中 | 如果计划声明了契约变化，检查对应 spec 文件是否在变更集中 |
| 是否出现计划外的重复修改点？ | 高 | 对比计划声明的"影响文件"与实际 git diff 范围 |
| 专项计划状态是否需要同步到 PLAN_MAP？ | 高 | 检测计划文档内的状态声明与索引表是否一致 |
| 原有测试和完成条件是否仍能证明目标达成？ | 低 | 保持人工 |

**建议**：实现 `check_plan_governance.py --drift` 模式，自动执行上述"高"可行性项。

## 四、变更时的主动提醒

### 7. 没有 pre-commit 钩子

**现状**：检查脚本只在 CI 或手动运行时生效。最危险的漂移往往发生在 commit 时——开发者改了一个被计划覆盖的文件但没有意识到。

**建议**：提供可选 pre-commit 钩子脚本：

```bash
#!/bin/bash
# .git/hooks/pre-commit (由 init_plan_governance.py --install-hooks 生成)
# 检测当前变更涉及的文件是否与活跃计划的影响范围重叠
python3 scripts/check_plan_governance.py --pre-commit
```

当 commit 涉及的文件与某个"实施中"或"待实施"计划的影响范围重叠时，输出提示：

```
WARNING: 本次变更涉及以下文件，这些文件被活跃计划声明为影响范围：
  src/api/handler.go  ← 计划「api-compat-migration」(实施中) 的影响范围
建议：在 commit message 中引用该计划 (e.g. "feat(api): [api-compat-migration] ...")
```

不阻断 commit，仅做提醒。

### 8. 合同/契约变化无自动关联验证

**现状**：当计划的"公共契约变化"章节声明了 API/Schema 变更，但实际 spec/Schema 文件没有被修改时，计划声明和实际变更之间存在脱节。

**建议**：

- 如果计划文档声明了契约变化（如"OpenAPI spec 将新增字段 X"），检查脚本验证相关 spec 文件是否在同一批变更中
- 实现需要计划文档中的契约声明有明确的目标文件路径

```markdown
## 公共契约变化

| 变更 | 目标文件 |
|---|---|
| 新增 `POST /api/v2/grants` 端点 | `specs/openapi.yaml` |
| `Grant.status` 新增 `archived` 枚举值 | `src/types/grant.go` |
```

## 五、治理范围完整性

### 9. "幽灵计划"——孤立计划文件

**现状**：检查脚本验证了"`PLAN_MAP.md` 引用的计划文件是否存在"（正向），但没有检查反向——`docs/plans/` 下是否有不在索引表中的孤立文件。

**风险**：计划文件被创建后忘记加入索引；或者文件被改名/移走但旧文件残留。

**建议**：

- 检查脚本扫描 `docs/plans/*.md`，与 `PLAN_MAP.md` 索引表做差集
- 发现孤立文件时发出 `WARNING`

```python
def find_orphan_plans(docs_dir, indexed_plans):
    all_plan_files = set(p.stem for p in (docs_dir / "plans").glob("*.md"))
    return all_plan_files - set(indexed_plans.keys())
```

### 10. 阶段门禁的自动化校验

**现状**：设计文档第 10 节定义了阶段门禁（目标明确、Step 0 可执行、无阻塞问题等），但这些条件是否满足完全依赖人工判断。

**可自动化部分**：

| 门禁条件 | 自动化 | 方案 |
|---|---|---|
| 当前阶段目标、范围和非目标明确 | 中 | 检查非空且超过最小长度 |
| 角色、信任边界和不变量明确 | 低 | 保持人工 |
| 公共契约及失败策略明确 | 低 | 保持人工 |
| Step 0 和验收方式可执行 | 高 | 同第 1 项增强 |
| 无阻塞当前阶段的未决问题 | 高 | 解析"未决问题"表，检查"是否阻塞当前阶段=是"且"状态≠已决定/已延后" |

**建议**：检查脚本解析每个计划的"未决问题"表，标记出声明为"阻塞当前阶段=是"且状态仍为"待确认/未解决"的项。

## 六、优先级建议

按"防漂移效果 / 实现成本"排序：

| 优先级 | 优化项 | 效果 | 成本 | 理由 |
|---|---|---|---|---|
| **P0** | 证据有效性检查增强 | 高 | 低 | 直接堵住"写了标题就当有证据"的漏洞 |
| **P0** | 计划停滞检测 | 高 | 低 | 防止"实施中"变成僵尸状态，影响后续决策 |
| **P1** | 依赖声明与正文交叉验证 | 中 | 低 | 半自动化，发现率高，实现简单 |
| **P1** | 同模块多计划冲突标记 | 高 | 中 | 防止静默覆盖，影响面大 |
| **P2** | 孤立计划文件检测 | 中 | 极低 | 纯机械检查，几行代码 |
| **P2** | 阶段阻塞项自动化 | 中 | 低 | 设计文档已有定义，只是未脚本化 |
| **P2** | 已完成计划被修改检测 | 中 | 中 | 需要引入 hash/摘要存储机制 |
| **P3** | pre-commit 钩子 | 中 | 中 | 需用户主动安装，但效果好 |
| **P3** | 漂移检查半自动化 (`--drift`) | 高 | 高 | 最有价值也最复杂，建议分步做 |
| **P3** | 契约变化关联验证 | 中 | 高 | 需要计划文档结构化声明契约目标 |

## 七、不建议的方向

以下方向在当前轻量定位下**不建议引入**：

| 方向 | 理由 |
|---|---|
| 看板/Kanban 集成 | 与设计文档的非目标冲突 |
| 自动状态流转 | 状态变化应是有意识的人工决策 |
| 计划工时/估算 | 偏离治理定位，进入项目管理范畴 |
| 多仓库计划联动 | 过度设计，当前阶段用交叉引用即可 |
| AI 自动漂移检测 | LLM 判断不可靠，且与"验收独立性"原则冲突 |
| 计划审批工作流 | 设计文档明确不引入正式审批流程 |
