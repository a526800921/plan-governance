# 架构图谱治理计划评审

> 评审日期：2026-07-24
> 对象：[架构图谱治理与三层图谱衔接](plans/architecture-graph-governance.md)
> 性质：独立分析报告；计划正文与 `PLAN_MAP.md` 仍是规范事实源。

## 结论

计划方向正确，且没有偏离“LLM 默认维护、人只在不确定时兜底”的基调：CLI、hook 和 GitNexus 只读地产生校验、影响或新鲜度候选；LLM 在证据充分时更新 YAML，语义歧义才上升人工确认。

当前不存在计划索引、状态、依赖或历史事实源漂移：`PLAN_MAP.md` 指向阶段 0，最后更新已同步为 2026-07-24；反向引用未发现旧草案重新成为事实源。当前阶段仍是“设计中”，不应进入阶段 1。

主要风险不在方案方向，而在阶段边界与契约收敛：已有多项确认决策尚未被 ModelPad 样本验证，也有同一事实在探索结论和公共契约中重复书写。

## 已确认且一致的方向

- 三层职责清晰：功能层记录业务/功能/流程；架构层记录模块、接口、数据与信任边界；GitNexus 保持代码事实源。
- API 技术契约归架构层；功能层只保留用户视角的对外能力及跨层关联。
- 功能层关系收敛为 `contains`、`depends_on`、`orchestrates`、`consumes`；`implements`、`exposes` 不再作为功能层内部关系。
- GitNexus UID 为可选精确索引；文件路径、全限定符号名和符号类型是长期代码锚点。
- 新鲜度流程是“只读发现候选 → LLM 依据证据更新 → 不确定时人工兜底”，没有把 YAML 写回权交给 hook 或 CLI。
- 影响分析采用保守跨层传播、行动分级和分层测试映射，不把图谱命中误写成“代码必改”。
- 新三层 Schema 可以干净切换，旧 v1 图谱只作为背景，不承担兼容与迁移成本。

## 发现的问题

### P1：当前阻塞项语义不准确

计划写为“无；架构节点最小集合与跨层关系方向待阶段 0 冻结”。后两项同时又是阶段 0 完成条件，因此它们是当前阶段的实质阻塞项，不应与“无”并列。

建议将其改为明确的两个阻塞项：

1. 基于 ModelPad 证据冻结最小架构节点集合；
2. 基于 `change_kind` 冻结功能→架构、架构→代码的关系方向和升级条件。

这样能避免严格检查通过被误读为阶段已经具备实施准入。

### P1：LLM 默认维护原则正确，但缺少可执行的证据门槛

目前已定义“证据充分可自动更新、歧义才人工确认”，但未定义何为充分，以及候选报告的最小内容。没有这层约束时，不同 LLM 可能对同一代码变化作出不同写回判断。

建议在阶段 0 补一个最小维护契约，而非增加人工审批：

- 候选必须列出变更类型、受影响节点/关系、证据文件与定位、置信结论；
- 仅代码锚点变化可由代码证据确认；业务关系或节点拆分/合并至少需要测试、API 契约或产品文档等语义证据；
- 自动写入后必须运行新 Schema 的 `validate`，并保留影响分析前后差异；
- 证据冲突、多个候选映射、关系方向不唯一时自动停止写回并上升确认。

这会强化 LLM 主维护，而不是把工作重新交回人工。

### P2：后续阶段细节过早进入“公共契约”

`change_kind` 枚举、行动分级、测试映射、新鲜度、生命周期和跨层升级规则已经写入“公共契约变化”，但阶段 1-3 仍未取得 ModelPad 样本。其方向已经由用户确认，应保留；风险在于把尚未通过样本验证的 CLI 字段和输出语义当成不可变实现契约。

建议保留这些决定，但明确分层：

- 阶段 0：作为设计原则与验收意图；
- 阶段 1：冻结目录加载、节点/关系、跨文件 ID 和代码锚点 Schema；
- 阶段 2：冻结重绑定与代码级传播；
- 阶段 3：根据真实计划与测试样本冻结 `change_kind`、行动分级和测试映射输出。

### P2：同一决策在多个章节重复，存在后续文档漂移风险

API 归属、关系收缩、UID 规则、目录组织等分别出现在“需求探索”“公共契约变化”“当前阶段范围”和“未决问题”。探索章节保留用户确认过程是合理的，但字段级定义应只在“公共契约变化”中作为规范表述，其他章节链接或摘要即可。

### P2：干净切换缺少明确的切换判定点

“旧 v1 仅作背景”方向清晰，但还缺少何时停止把旧图谱作为阶段 0 基线、何时让新 `index.yaml` 成为唯一 CLI 输入的切换条件。

建议将切换点固定为：新目录 Schema 校验、最小架构样本、三类 ModelPad 场景和新 CLI 输入路径均通过后，计划前置门禁才改指向新图谱。阶段 0 仍可把旧图谱仅作为只读基线。

### P3：几个已确认能力仍缺少边界样本

- 目录加载：`index.yaml` 的发现规则、跨文件关系放置位置、重复 ID 与缺失文件的失败语义未定义。
- 生命周期：`deprecated`、`retired` 的校验与查询行为尚无 fixture。
- `change_kind`：`behavior_change` 与功能下线、性能/可靠性改动的归类尚未规定；可先在 ModelPad 样本中观察，不急于扩充枚举。
- 测试映射：应明确“无映射”只是报告缺口，不阻断尚未建立测试映射的早期项目。

## 漂移判断

| 检查项 | 结论 | 依据 |
|---|---|---|
| 计划状态与索引 | 无漂移 | `PLAN_MAP.md` 与专项计划均为阶段 0、设计中、最后更新 2026-07-24 |
| 旧草案重新成为事实源 | 未发现 | 反模式搜索命中仅为规则和历史验证文本 |
| 功能层直接耦合 GitNexus | 无方向漂移 | 新计划明确 UID 收缩为架构层可选映射 |
| LLM 为主维护 | 无方向漂移，存在执行细节缺口 | 新鲜度与自动更新均由 LLM 处理；CLI/hook 只读 |
| 阶段边界 | 有轻度漂移风险 | 阶段 3 输出细节已进入阶段 0 公共契约 |
| 当前阻塞项 | 有表述漂移 | “无”与未冻结的阶段 0 完成条件并存 |

## 复核命令与结果

```bash
plan-governance-cli check .
plan-governance-cli check . --strict-readiness
plan-governance-cli check . --stale-days
git diff --check
```

以上命令均通过。严格检查通过的原因是计划仍处于“设计中”；它不替代阶段 0 的样本验证和独立准入复核。

## 建议的下一步

先不要实现 CLI 或迁移 ModelPad。应先完成一个小而可复现的阶段 0 设计包：

1. 盘点 ModelPad，产出最小架构节点候选及其证据；
2. 为五类 `change_kind` 至少各选一个可解释样本，冻结跨层传播矩阵；
3. 定义 LLM 候选报告与自动写入的证据门槛；
4. 明确新目录 `index.yaml` 的加载与失败语义；
5. 据此更新计划、完成独立准入复核，再决定是否进入阶段 1。

- 已将最小架构节点集合、跨层方向/升级条件和 LLM 证据门槛同步为 `PLAN_MAP.md` 的当前阻塞项，不再以“无阻塞项”表述。
- 已明确需求前置默认只查询功能层；API、数据、安全、共享架构或代码定位信号才逐层下钻。
- 已将 LLM 候选报告、自动写入证据门槛、校验闭环和上升确认边界写入阶段 0 完成条件。
- 已明确新 Schema 切换到计划前置门禁的条件；旧图谱在阶段 0 仅作只读基线。

其余问题仍需通过 ModelPad 样本验证后才能关闭，不能以本报告或文档修改替代阶段 0 的独立准入复核。
