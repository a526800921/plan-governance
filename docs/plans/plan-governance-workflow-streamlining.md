# 计划：协作流程减负与技能结构优化

## 执行交接

- **要解决的问题**：减少低风险任务的复核、重复读取与重复验证，保留高影响检查，并把 AI 技术验证、用户体验及性能验收连成闭环。
- **当前授权**：用户于 2026-09-06 明确要求推进本计划，并将复核分流落实到共享 skill，供后续会话遵循。先完成阶段 0 设计及阶段 1 自身准入，再实施；不重复请求已明确的实施授权。
- **本计划采用的方向**：简单改动当前 AI 自验；高影响保留独立复核；一个 skill 配三份按需参考；项目依赖已安装 skill 或 CLI；用户接受后关闭功能计划。
- **下一步入口**：阶段 1 技术完成已[独立验收通过](../reviews/plan-governance-workflow-streamlining-completion-review-20260906.md#第三轮通过)，当前等待用户验收；另获授权的 `1.0.0` 发布和本地 CLI/skill 更新已完成，结果见[发布维护](plan-governance-distribution-setup.md#2026-09-06-100-发布维护)。详细目标见 F/R/E 编号；历史过程按需读取，不要求接手者重读全部聊天和旧计划。
- **这批计划的关系**：前置已提交技术成果与本次推进授权 → 本计划设计收敛 → 实施及用户验收。宿主回放计划继续作为独立支线，不要求先完成其阶段 2。

## 执行顺序

以下是两个既有阶段内部的工作顺序，不新增阶段、逐项审批或逐项独立复核。本轮已获推进及共享 skill 实施授权；阶段 1 已独立准入，当前实施中。

| 顺序 | 工作及交付 | 结束判据 |
|---|---|---|
| 1 · 阶段 0 | 核对前置最终树、安装版本及未提交差异；按[成果对照](#与前置及相关计划的边界)保留已交付能力，固定剩余差距和代表性旧流程基线 | 已覆盖、部分覆盖、未覆盖可区分；证据可访问，最终交接基线与本次推进授权可定位后解除 B01 |
| 2 · 阶段 0 | 收敛[三项设计交付](#阶段-0-设计交付)：风险复核与阶段门、技术完成与用户接受、规则读取与旧项目兼容 | 给出真实记录方式、旧/新正反样本和受影响文件；不伪造独立通过、不制造额外状态事实源 |
| 3 · 阶段 0 | 固定行为样本、验证命令和实施范围，完成适用独立设计复核；随后准备阶段 1 自身准入 | B02 收敛；阶段 0 设计结论和阶段 1 准入分别可判断，能复用相同设计证据而不重复整套审查 |
| 4 · 阶段 1 | 先落地验收闭环与风险分流（F01—F03、R01），同步必要的计划/机器判定；规则直接写入目标参考文件 | 低风险自验、高影响独立、技术完成待用户验收的行为一致；新增能力随改随验 |
| 5 · 阶段 1 | 在同一规则来源落实证据复用、增量复验、恢复读取、输出交接及 subagent 调度（R02—R04、E01—E04） | 可信证据可复用，变化/冲突触发适用补验，同一未修正阻塞不重复送审；等待不越界 |
| 6 · 阶段 1 | 先使参考资源和只读 CLI 入口可达，再精简 SKILL 与项目受管块，完成分发和旧项目兼容验证 | skill-only、CLI-only、版本差异和缺依赖均行为明确；受管块外字节和既有文档保持 |
| 7 · 阶段 1 | 完成代表性任务对照（E05）、受影响回归及必要独立完成复核，交用户体验验收 | 质量反例仍能检出；可说明读取/复核/时长变化及局限；用户接受后才关闭本计划 |

第 4—6 项可以在不影响受审对象的前提下准备互不依赖的材料；共享规则单一写入。不要先扩写长 SKILL 再整份搬家；三份参考从规则落地起就是目标位置。正式 CI/发布检查沿用前置契约，发布、安装同步和其他项目操作不包含在本计划默认实施授权中。

历史记录（本次推进授权前）：2026-09-06 执行前整理时，前置阶段 0—4 已完成独立技术验收，见[最终报告](../reviews/iterative-governance-reliability-stage4-completion-review-20260906.md#第二轮通过)。本计划继续保持阶段 0 设计中；前置用户接受记录尚待补齐，不能将技术验收、提交请求或“一会开始执行”自动记为产品接受。本轮授权是整理文档，尚未开始实现。

## 目标

- 减少无效追问、重复复核和无理由的全量验证，同时保留授权边界、缺陷发现与独立判断。
- 补齐可观察验收、相关性能基线、必要的早期体验、AI 自主修复和用户最终验收闭环。
- 精简 skill 入口及项目受管规则，按需读取详细说明，避免多处维护同一契约。
- 降低执行中的重复读取、证据交接和独立复核调度开销，用代表性任务观察上下文压力与实际完成时长。
- 只处理前置计划完成后仍存在的差距，以实际样本判断效果，不承诺未经测量的耗时改善比例。

## 非目标

- 不接管或重开前置计划；不重复实现其门禁修复、统一 verify/发布恢复、文档职责和可选证据绑定。
- 不取消现行门禁后再用新规则自我批准；不恢复已废弃的整计划自主执行运行时，不默认创建 goal 或调度服务。
- 不将所有生命周期阶段拆成独立 skills，不强制所有项目采用用户逐阶段签收，不增加固定文档组合或统一性能数值。
- 不为未安装 skill 和 CLI 的环境生成项目内完整治理规则副本；治理规则的读取以已安装 skill 或 CLI 为前提。
- 不迁移历史项目、不清理用户目录残留、不解除宿主回放阻塞；提交、发布、全局同步和 Docker/TunnelPad 实际操作另按授权执行。

## 需求探索

### 已确认事实与结论

- 用户通常提出功能，经 grilling 确认后持续实施；AI 先功能和运行验证，用户再查看、操作并观察 CPU、内存及磁盘读写；用户接受后关闭功能计划。
- 原范围小问题由 AI 自行修复、复验及必要的重新送审；新取舍、授权变化和无法自行解决的问题才升级。新点子或较大改动另开计划。
- 用户反馈复核时间占用较多，要求纳入原报告的 F01—F03 和 R01—R04；本次明确选择独立后续计划，不再合并到正在执行的计划。
- 用户于 2026-09-06 明确要求：后续简单改动先由当前 AI 自行复核，不每次走独立复核。用户随后澄清这不是仅当前会话的临时例外，须落实到共享 skill 供其他会话遵循；具体边界见[复核分流约定](#按风险选择自验或独立复核)；不把自验结果写成独立验收。
- 用户已确认安装前提：精简项目 AGENTS/CLAUDE 后，无需支持将项目复制到既未安装 skill、也未安装 CLI 的环境仍能读取完整规则；不新增项目内完整规则文档。
- 用户要求补入任务执行记录对照发现的五项遗漏，并反馈：自从独立复核接入 subagent，整个计划的执行时长感觉明显增加。这是已确认的使用反馈，尚无同等任务的前后对照或增幅测量，不能将全部耗时归因于 subagent。
- 已确认场景直接沿用，不重复完整 grilling。下列尚未确定的技术策略保留为候选，不把方案建议写成已完成的用户选择。

### 候选方案与取舍

推荐保留一个治理入口，按需拆出计划/契约、验证/复核及 CLI 操作参考，复用已有 grilling 和项目专业工具。入口保留任务分流、必要底线和明确读取条件；细节只维护一处。安装前提已确认，以下具体划分及 CLI 读取入口仍是待对照前置成果的设计提案，不代表已实施或整个设计已通过。

未定事项集中在[阶段 0 设计交付](#阶段-0-设计交付)，不把每个文件名或低影响实现细节升级给用户。优先复用现有枚举和记录区；确需改变公共字段时先明确差异及兼容策略。

### 入口精简与按需拆分提案

保留一个 `plan-governance` skill，不按生命周期另建多个 skills。下表路径相对于 `resources/skill/`；尚未创建参考文件。

| 内容 | 处理与拟议位置 | 读取条件 |
|---|---|---|
| 启用判定、任务分流、当前步骤和下一决策 | 合并到 `SKILL.md` 的简短入口，明确普通小改、已有计划内反馈和新计划的区别 | skill 被调用时 |
| 授权复用、不可自批失败、用户最终验收等必要底线 | `SKILL.md` 保留简短明确的约束，并链接适用细节 | 不依赖读完全部参考才能知道底线 |
| 文档职责、需求探索输出、状态/阶段、事实源与同步、历史草案 | 去重后放入 `references/planning.md` | 新建或调整计划、范围、契约、状态时 |
| Step 0、验证、独立复核、修复重审、证据复用、用户验收 | 放入 `references/verification.md`，给出适用条件和停止条件 | 准备阶段证据、验证、复核或处理验收反馈时；只读适用部分 |
| 初始化、升级、漂移检查、证据绑定、图谱及 hook 操作 | 从入口移至 `references/cli.md`，说明已存在的公开命令和资源查找方式 | 确实需要相应 CLI 操作时 |
| 计划、ADR、migration、spec 等模板 | 保留 `assets/`，引用现有模板，不把模板正文复制到入口 | 确需创建对应文档时 |

grilling 继续复用已有技能；治理入口只负责何时调用、已确认内容何时可跳过及应留下哪些输出。普通小改不要求读完三份参考，也不强制建计划；已有计划覆盖时按受影响内容更新。拆文件本身不改变复核时点，复核减负仍须落实 R01—R04。

### 安装前提与项目入口

项目 AGENTS/CLAUDE 的受管块拟只保留治理启用说明、规则读取方式、项目事实源路径和少量必要底线；项目特有约束仍在项目中维护。通用细节由安装资源提供，不再生成另一份完整项目规则。迁移须保留受管块之外的用户内容，继续遵守现有仅更新 agent 规则和升级不覆盖项目文档的边界。

- 已安装 skill：从宿主发现的 skill 入口读取，并按需读取该安装包内的参考和模板，不硬编码 `~/.agents` 等安装路径。
- 仅安装 CLI：需要补充公开的只读规则读取入口。当前 CLI 尚无该能力；候选为 `plan-governance-cli guide [topic]`，先返回简短入口，再按主题返回包内参考。命令名尚未冻结，设计要求是不依赖当前工作目录、不下载、不安装、不写项目文件；它不是现有命令，也不能以 `setup` 代替只读查询。
- 两者都安装：一次治理工作沿用同一份已选规则来源及其参考，不混读不同安装版本的正文；实际调用 CLI 时核对所需能力，遇到相关契约不兼容再处理，不为所有版本差异增加审批。
- 两者都未安装：明确指出治理规则读取的安装前提缺失，不自动安装、不假定已遵循不可得规则，也不因此阻塞无关的普通工作。

“skill 或 CLI”是规则可发现性的前提，不意味着只有 skill 就能运行 CLI 命令；当前阶段若需要实际 CLI 检查，仍需相应可执行工具。参考文件及 CLI 读取内容应复用同一份包资源，并纳入分发清单验证，不另维护重复正文。

## 公共契约变化

用户已授权将风险分流落实到通用 skill/生成规则/检查器，以下为实施及验证目标；设计准入前尚未替代现行机器契约。来源编号用于追溯原报告；此后的具体规则以本计划收敛结果为准。

| 来源 | 拟议差异与验收要点 |
|---|---|
| F01 | grilling 收敛时固定少量场景、输入/前置、操作和可观察结果；相关性能指标与可比环境、负载、窗口一起确定，不发明通用阈值 |
| F02 | 交互或方案明显不确定时先交付关键流程供体验；明确小改不增加中途签收，不把未回复当作接受，可继续不依赖反馈的工作 |
| F03 | 技术验证提供可复验命令/步骤及实际结果；原范围小缺陷自主修复、复验；采用该协作方式的功能计划经用户接受后关闭，技术完成不冒充用户接受 |
| R01 | 用户已确认简单、低风险且边界、影响与验证明确的改动由当前 AI 自验，不逐次独立复核；高影响变更保留独立复核；独立复核时点及必要例外按下文风险分流候选收敛，不按代码行数判断风险；现行阶段规则变更先明确兼容 |
| R02 | 普通自验失败由当前 AI 修复、复验；已经触发独立复核的缺陷重审聚焦原阻塞、修复差异及受影响回归，引用仍有效的原证据；失败记录保留，由独立复核者追加新结论，不改分类自批 |
| R03 | 可信全量证据覆盖当前受审工作树、依赖、配置、环境和验证契约时可复用，复核者核对并复验关键风险点；相关变化、缺失或冲突时补验，版本号或 HEAD 相同不够 |
| R04 | 同范围行为后测与完成复核适用时合并；复核者未参与实施或测试编写，先盲测再对照预期，行为与机械结果分别记录 |
| 初次审计：入口与资源 | 精简 SKILL.md 和受管 AGENTS/CLAUDE，详细手册按需加载；明确 npm CLI 与 skill 资源位置，参考文件和模板随分发可达，不自动删除安装目录残留 |
| 初次审计：追问、授权和文档验证 | 补齐已确认方案跳过、非阻塞追问退出和既有授权复用；纯文档执行适用检查并说明代码覆盖率不适用，不为字段创建无价值测试 |

### 按风险选择自验或独立复核

2026-09-06 用户已确认：后续简单改动先由当前 AI 自行复核，不每次走独立复核。随后用户明确要求后续会话使用 skill 时也遵循统一规范。本轮将约定落地到共享 skill、模板、生成器和适用机器判定；现有 AGENTS/CLAUDE 中临时项目说明在共享规则生效后移除。本轮不安装或同步用户目录中的已分发副本。下表是共享规则的风险边界。自验、独立复核和用户产品验收分别记录，不能把自验结果写成独立验收通过。

| 情况 | 推荐处理 | 适用边界与例子 |
|---|---|---|
| 低风险，目标和影响范围明确，易撤销且实际验证足够 | 当前 AI 检查差异、执行适用测试/运行验证，修复并复验；简要记录结果，不默认派独立 subagent 或新建复核报告 | 提示文案、局部 UI 调整、已定位且影响有限的小 bug；普通功能若满足同样条件也可自验，是否进入计划本身不决定独立复核 |
| 高影响变更 | 独立复核；在关键设计决策前或完成时安排必要检查，按风险选时点，不给每个内部步骤单独派发 | 安全/权限/公开暴露、数据完整性或迁移、核心公共契约和生命周期、较大范围共享逻辑、难以撤销的操作。少量代码或一行配置也可能属于高影响 |
| 暂时无法判定风险、反复修复无效或证据冲突 | 先由当前 AI 补事实和定向验证；仍存在实质不确定或盲点时，说明原因并请求定向独立检查 | 不把每个未知细节都升级成全量复核，也不凭自信判为低风险；用户明确要求独立复核时保留该要求 |

可逆性同时评估实际外部后果，不以代码可回滚替代操作可撤销。执行中发现影响超出原分类时重新评估，不能等自验结束后仍按旧范围放行。已有独立失败结论或未解除的有效阻塞不因改分类而消失。用户最终查看、操作和相关性能验收保持原约定；普通小问题仍自主闭环，高影响动作是否需要用户授权继续按既有授权边界判断。

新策略下阶段转换或计划收尾本身不自动触发独立复核，是否需要由实际风险及适用契约决定。阶段 0 须明确低风险自验在计划、check/workset 和生成规则中的一致表达，以及现有强制独立准入记录的兼容方式；不得用“自验通过”伪填“独立复核通过”。本计划对跨项目准入/复核保障的规则修改本身按高影响变更处理，不能使用拟议豁免批准自身；正在执行的前置计划继续遵守其原门禁。

| 补充项 | 目标行为与边界 | 拟归属 |
|---|---|---|
| E01 恢复与按需读取 | 继续任务或上下文压缩后，先从现有工作集、当前阶段和最近证据定位目标、授权、阻塞及下一动作，并核对实际工作树。历史和代码按缺口读取；已有材料不足或变化时扩大读取，不机械重读全计划/全库。复用现有记录，不另建第二份状态事实源 | planning |

### Subagent 复核时长与调度

独立复核可能增加串行等待：实施者自验后，复核者还需要获取上下文、检查风险、执行必要验证并返回结论。它可减少等待用户逐项安排的停顿，但不是天然的加速保证。前置阶段 4 的全量测试通过后，独立实盘仍发现 [D02/D03](../reviews/iterative-governance-reliability-stage4-completion-review-20260906.md#第一轮未通过)；此类检查及必要修复保留，减负重点是重复准备、重跑和交接。

- 先按 R01 判断是否需要独立复核；仅在需要时，拟默认由一位独立复核负责人统筹该复核点。专门子复核仅用于明确、可分的风险，划清范围，合并可共用的机械检查，不为每个内部步骤新增复核。专家的有效阻塞不得被汇总结果或多数通过覆盖；实现者及测试作者不能充当自己的独立验收者。
- 派发时提供当前范围、契约、变化、关键风险和 E02 证据入口，使复核者能够自行查证；不发送完整聊天历史替代任务说明。需要行为盲测时，预期答案按 R04 隔离，紧凑交接不能破坏独立判断。
- 等待复核时可推进已授权、无需该结论的准备工作；不得越过门禁，也不得改动受审对象及其依赖、配置、环境、测试数据。若并行变化影响证据，按实际范围标记失效并补验。
- 同一未修正阻塞不重复派发求通过；修复后进行适用的独立增量重审，影响扩大则扩大复验。等待优先使用宿主的有界等待/状态变化机制，减少无变化轮询和重复追问；不可用、超时或失败仍保留阻塞，不因耗时自动通过。
- 效果对照区分必要审查/缺陷修复、重新读取/重复验证、派发/等待/交接，以及用户等待、额度中断等非执行时间；关注决定任务何时结束的串行环节，并行子任务的耗时不能直接相加冒充总时长。任务规模和风险不同的历史案例仅作线索，不据此宣称固定加速比例，也不为节省时间降低完成条件。

## 不变量

- 原授权持续有效，范围和高影响边界变化时才重新确认；独立复核不能代替用户授权。
- 失败、不可用或冲突不得自行批准；允许授权范围内补证据和修复，未解除前不越过适用门禁。
- 变更风险决定检查深度；可选风格建议不自动成为阻塞，不为每个样本、微小修复或报告另造阶段门。
- 当前阶段写细、后续阶段写粗；新增规则生效前遵守现行准入，不用拟议减负规则放行自身。
- 单一事实源和单一写入边界保持；状态、关系、阻塞及证据链接同步地图，历史记录不覆盖。

### 已收敛的实施契约

D1 采用显式、向后兼容的风险策略：

- 当前阶段摘要可选字段 `复核策略`，唯一启用值为 `风险分流`；字段缺省完全沿用旧独立准入契约。空值、未知值、重复字段或新旧结构歧义不能默认低风险。
- 启用后，摘要以 `最新阶段复核` 链接替代 `最新独立准入复核`。固定章节 `最新阶段复核` 包含 `日期、阶段、方式、风险、风险依据、结论、证据、复核者`；`方式` 为 `自验/独立`，`风险` 为 `低风险/高影响/待判断`。通过必须有有效日期、当前阶段、非占位证据/依据/身份；自验只可用于低风险，待判断不可通过。风险判断覆盖范围、实际后果、可逆性及验证充分性，机器只验证声明结构，不推断真实风险。
- 结论按明确前缀声明结果：以 `通过 / 未通过` 等未选择候选开头时，无论其后标点或待选说明是什么，都视为未知；明确通过后的修复说明不受影响；明确失败前缀优先；明确 `通过` 前缀支持常见句末符号（包括 `通过。`）；其后的修复说明可提及历史冲突/超时，不因此重判失败；没有通过前缀的不可用/超时/证据冲突等声明仍失败。结构化有效阻塞独立保留，不能由通过说明覆盖；机器不推断自由说明真实性。
- `阶段复核记录` 是追加式八列表：`日期、类型、阶段、方式、风险、结论、证据、复核者`。最新当前阶段记录与最新表的日期、方式、风险、结论、证据和身份一致；失败/不可用/超时/证据冲突不算通过，修复另追加结果。普通无计划小改只简报自验，不建立这些表。
- 旧独立记录不迁移、不删除。显式启用新策略时，当前阶段仍有旧独立失败、未解除的历史失败或最新/历史冲突，仍阻塞；补充适格独立通过后更新旧最新结论并保留历史，才可解除。新策略内最后一次独立记录失败也不能被后续自验遮蔽。上一阶段历史不自动封锁当前阶段。
- check、workset 和 hook 共用判定；保留 JSON schema 1、键及动作枚举。有效低风险待自验用 `design/verify`，有效复核通过但地图仍设计中用 `design/sync`；高影响待独立复核用 `independent_review`。显式失败用 `blocked/resolve_blocker`，歧义用 `unknown/unknown`。默认 WARNING、活跃计划严格 ERROR 的既有分层保持。
- 新模板默认声明风险分流，但风险与复核结果保持待判断/未进行，绝不生成已通过。旧项目升级只更新受管入口，不自动迁移计划。旧 CLI 不理解新策略时可能拒绝新计划的严格准入，必须显式更新所用 CLI；不把旧版误报伪装成新能力。
- 不扩展 attestation 引擎或 hook 权限。明确记录的证据失效继续作为阻塞；实际内容/环境/依赖变化由验证规则及适用的 `check --check-attestations --strict-readiness` 核对，不能声称 workset 自动检测文件 hash 或环境漂移。

D2 不增加生命周期或 JSON 枚举。技术完成待用户验收的适用功能计划保持 `实施中`；在最近实施/验证记录放入技术结果、证据和待验收项，当前阶段显式 `下一动作：等待用户验收`。workset 将此映射为已有 `none`，reason 明确等待用户验收且不自动关闭。原范围反馈自主修复/复验，新需求重新归属；用户沉默、提交和技术通过均不补写接受。纯机械文档同步或普通小改不增加逐次签收。
