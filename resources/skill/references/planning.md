# 计划与契约

从 [skill 入口](../SKILL.md) 判断是否需要治理。本页维护计划与决策，验证和阶段完成见 [verification](verification.md)；CLI 入口为 `guide planning`。

## 需求探索与 grilling

先利用上下文和可查证事实补齐需求。普通可逆细节自主决定；只有必须由用户决定、且会实质改变结果或授权边界的缺口才提问。问题聚焦当前取舍，不因某个字段未填完整就重做访谈或重复确认已有决定。

需要深入探索或用户点名时可使用 `grill-me`；它是可选方法，缺失不阻塞任务，可直接澄清关键问题。需要治理时将已确认的范围、重要假设与未决取舍记入计划；只有新的必要决定等待回答，其余已授权工作继续。

## 仓库模型

只创建当前任务需要的文档，不预建完整目录或 PRD/spec/ADR 套装。

| 文档 | 职责 |
|---|---|
| `docs/PLAN_MAP.md` | 计划状态、阶段、关系、阻塞及证据入口 |
| `docs/plans/*.md` | 本次目标、范围、决策、差异与验证证据，计划文件平铺 |
| Schema/OpenAPI 或 `docs/specs/` | 现行公共契约，优先复用已有来源 |
| `docs/adr/`、`docs/migrations/` | 确有需要时记录长期架构决策或迁移步骤 |
| `docs/reviews/`、`docs/fixtures/` | 必要复核及可复验样本，代码 fixture 放 `tests/fixtures/` |

## 多文档同步规则

同一事实保留一个权威来源，其他文档引用。决策或结果改变后，同步地图及实际受影响的索引/引用；同一组已收敛变化可合并同步，不为每次保存增加流程。用 `rg` 定向检查相关计划名、关键字段和链接，不重扫无关历史。

## 草案和历史文档处理

历史草案、旧计划与临时分析保留为背景，不承载新规范。新事实写入当前计划或适用契约；用户明确指定的文档位置优先。已替代内容通过链接说明关系，避免重复改写历史。

## 漂移检查

目标、授权、关键契约或高影响后果变化时，重新判断受影响范围的准入与验证；等待必要取舍期间，可继续无依赖的已授权工作。普通反馈、测试结果和状态更新在当前任务内处理并同步，不自动暂停、重开阶段或再索取授权。范围调整不能移走真实阻塞。

## 执行与恢复

沿用当前有效策略和已确认决定，只展开本次差异、证据缺口及直接依赖。跨阶段工作按 [阶段门](verification.md#step-0-与阶段门)判断，每阶段有自身基线与完成条件；上一阶段通过不自动放行下一阶段。未来事项需注明承接范围与依赖，不以未准入的后续工作阻断无关的当前交付。

文档变更后做适用链接、结构和引用检查，运行所选版本的 `plan-governance-cli check .`；准入/发布使用 `--strict-readiness`。纯落档不重复代码测试。用户验收与证据真实性按 verification，不以文档格式通过替代。

## 格式附录：写入地图时读取

### 推荐状态

| 状态 | 含义 |
|---|---|
| 候选 | 尚未承诺实施 |
| 设计中 | 明确范围、契约与准入 |
| 待实施 | 当前阶段已准入 |
| 实施中 | 执行中，或技术完成等待适用用户验收 |
| 已完成 | 证据、验证及适用验收齐备 |
| 已替代、已合并、已废弃 | 终态，保留关系和原因 |

### 停滞检查

`## 计划索引` 下依次使用 `### 未完成`、`### 已完成`、`### 已废弃` 三张六列表；每个计划只出现一次。已替代/已合并归入已废弃分表，行内保留真实状态。无对应计划时保留表头。

| 计划 | 状态 | 当前阶段 | 最后更新 | 依赖 | 证据 |
|---|---|---|---|---|---|

`最后更新` 使用 YYYY-MM-DD，在状态、阶段、依赖、范围、阻塞或验证结果变化时同步；不从文件时间或 Git 推断。`check --stale-days [N]` 可提示活跃计划停滞，默认 10 天，不自动改变状态。
