# 存量计划迁移

仅当用户明确要求迁移存量计划时使用本参考。计划目录存在、工具升级或主 skill 更新都不构成迁移授权。日常治理只读取计划索引，不主动移动或重命名文件。

本流程处理 `docs/plans/*.md` 等存量计划搬入 `docs/plans/YYYYMMDD/`，并修复由计划路径变化造成的引用。迁移 `reviews`、`data-quality` 或其他文档必须属于用户明确授权的范围；一般命名建议不会触发这些目录的批量重命名。

## 迁移前核对

1. 读取项目 `AGENTS.md`、`docs/PLAN_MAP.md`、所有受影响计划及适用的 [verification](verification.md) 规则。
2. 核对工作区差异、地图登记、所有候选平铺计划、日期目录目标占用、Markdown 引用和 attestation。
3. 建立源路径、目标路径、创建日期、日期来源和引用影响清单。先处理日期无法确认、目标冲突、未登记文件或本地修改不清等问题；未解决前不要移动文件。
4. 创建日期优先取 Git 首次添加记录。仅当正文明确记载创建日期时，才可回退使用正文日期。不得用文件修改时间或最后更新日期推断创建日期。

## 执行与验证

按确认后的映射移动文件，保留原文件名、计划身份、内容、状态、阶段和历史证据。同步更新 `PLAN_MAP.md` 和指向这些计划的文档链接；源文件层级变化导致相对 Markdown 链接失效时，重算其相对路径并保留锚点。代码块中的示例路径不视为引用。

不要改写旧 attestation。检查快照记录的计划路径、地图 hash 和替代关系；如果不能通过项目 CLI 建立可信的后继快照，保留旧快照并报告 `needs_review`，不要手工编辑 JSON 制造通过状态。

完成后确认源路径已清空、每个目标文件只出现一次、索引指向真实路径、所有受影响的本地链接可达，并按项目规则检查 checker、workset 和 attestation。若检查失败，依据源/目标映射恢复文件和引用，报告实际恢复范围及尚未解决的问题。

只处理用户授权的仓库和文档范围。不要顺便迁移其他项目、安装依赖或发布 npm 包。
